# Phase 4 — AI Monitoring, Evaluation and Reliability Architecture

**Project:** Forge Athletic (`F:\Fitness Coach`)  
**Phase:** 4  
**Status:** Implemented in source; production rules/index deployment is blocked (see [Completion Report](./PHASE_4_COMPLETION_REPORT.md))  
**Date:** 25 November 2026

---

## 1. Purpose

Phase 4 adds three operational capabilities around the existing AI features without changing their models or their member-facing behaviour:

1. **AI telemetry** for workout recommendation and AI Coach runs.
2. **Offline, reproducible model evaluation** of the exact ONNX artifacts that ship in `public/models/`.
3. **Admin visibility** into recommendation health, AI Coach health, sanitised failures, and deployed model quality.

The design priority is:

> REAL DATA -> ACCURATE MONITORING -> REPRODUCIBLE EVALUATION -> ADMIN VISIBILITY -> SECURITY -> RELIABILITY

No dashboard number in Phase 4 is hard-coded, randomly generated, or inferred from a placeholder. Every live statistic is computed from stored monitoring events or saved AI Coach sessions. Every model-quality number comes from a static report generated offline from held-out data. When a denominator is absent, the UI displays `—` or `not measured`, never `0`.

## 2. Scope and non-goals

### In scope

- Fire-and-forget telemetry for the workout recommendation pipeline.
- Fire-and-forget telemetry for AI Coach session lifecycle, inference failures and saved outcomes.
- Bounded admin reads and pure aggregation functions.
- A new admin error log page.
- Rebuilding the two existing AI admin pages on real data.
- Offline evaluation of all four deployed ONNX models.
- Firestore rules, indexes, unit tests and security tests for the new data.
- Phase 4 documentation.

### Explicit non-goals

- Retraining, replacing or re-exporting an ONNX model.
- Changing form-classification thresholds or recommendation classes.
- Introducing a paid API, hosted inference, or a dedicated inference server.
- Moving ONNX Runtime Web or MediaPipe Pose Landmarker off the browser.
- Persisting camera frames, video, pose landmarks, workout answers, free text, or member goals.
- Redesigning the admin visual language.
- Adding real-time charts, push alerts, or an on-call paging system.

## 4. Architectural decisions

### AD-1 — One top-level telemetry collection, not per-user admin scans

Events live in `ai_monitoring_events/{eventId}`. Admin queries filter by `feature`, `status` and `createdAt` directly. This avoids expensive and privacy-broad collection-group queries over member subcollections, and it gives rules a single, auditable write surface.

Trade-off: the collection needs retention management and indexes. Those are documented in [Database Schema](./PHASE_4_DATABASE_SCHEMA.md).

### AD-2 — Fire-and-forget, lossy by design

`trackAIEvent()` never returns a promise to its caller. It never awaits Firestore, never throws, and silently drops events when monitoring is disabled, offline, rate-limited, deduplicated, or when the queue is full.

Consequences:

- Monitoring cannot delay a prediction or break a session.
- Counts are a **lower bound**, not an audit ledger.
- Dropped events are acceptable; a lost workout is not.

### AD-3 — Store aggregates, not content

Event documents contain operational identifiers, model identity, aggregate counts, timings, and a short sanitised error message. They do not contain answers, media, landmarks, member text, or email addresses.

### AD-4 — Evaluation is a build artifact, not a database row

Official evaluation metrics are generated by a repository script and committed as JSON. No browser can write official metrics, and Firestore has no evaluation collection. This prevents a member or compromised client from inflating model quality.

### AD-5 — Admin reads are bounded and explicit

The admin pages use fixed windows (7/30/90 days) and hard caps (1,000 recommendation events, 500 coach/error events, 500 saved sessions). The UI reports when a cap is reached. It does not pretend to show complete history.

### AD-6 — Null is a first-class metric state

Aggregators return `null` when a denominator is zero. The UI renders `—` and labels the reason. A measured zero event count on a day with data is `0`; a day with no data is `null` and is not plotted.

## 5. Runtime data flows

### 5.1 Workout recommendation

```text
Page action
  -> recommendation.requested
  -> feature validation
       -> validation.passed | validation.failed
  -> model/schema load
       -> model.load_started
       -> model.load_succeeded | model.load_failed
  -> inference.started
  -> ONNX Runtime Web (local)
       -> inference.succeeded | inference.failed
  -> recommendation.generated | recommendation.failed
  -> plan persisted
       -> recommendation.saved | recommendation.save_failed
```

The recommendation call sites are in:

- `src/features/workout-recommendation/lib/inference.ts` (model load and inference).
- `src/features/workout-recommendation/lib/recommendationService.ts` (request, validation, generation, failure).
- `src/store/useRecommendationStore.ts` (plan save success/failure).

### 5.2 AI Coach

```text
Start camera/video session
  -> coach.session.started
  -> pose landmarker load (model.load_started + succeeded/failed)
  -> form classifier load (model.load_started + succeeded/failed)
  -> per-window scoring
       -> inference.failed only when a scoreable window throws
  -> finish / reset / unmount / camera error
       -> coach.session.completed
       -> coach.session.interrupted
       -> coach.session.failed
  -> save session
       -> coach.session.saved
```

The AI Coach call site is `src/pages/Dashboard/AICoachPage.tsx`. A `monitoringRef` stores the session reference and counters so terminal events are emitted exactly once. Cleanup on unmount closes an open attempt as `interrupted`.

### 5.3 Write path

| Stage | Behaviour |
| --- | --- |
| Eligibility | Requires configured Firestore, online browser, and a non-anonymous signed-in user. |
| Schema | Event type allowlist and optional-field allowlist from `src/features/ai-monitoring/types.ts`. |
| Sanitisation | URLs -> `[url]`, emails -> `[email]`, 32+ char token-like strings -> `[redacted]`, whitespace collapsed, 240-character cap. |
| Deduplication | Identical error signature (`eventType + sessionRef + errorCode + exercise`) suppressed for 60 seconds. |
| Rate limit | 100 events per rolling 60-second window per browser session. |
| Queue | In-memory, maximum 25 events; overflow forces an immediate flush. |
| Flush | 1,200 ms debounce or immediate on overflow; one `setDoc` per event; `Promise.allSettled`. |
| Failure | Swallowed. No retry, no user-visible error, no local persistence. |

The server timestamp is applied by Firestore (`serverTimestamp()`), not by the client clock. Rules require the stored `createdAt` to equal `request.time`.

### 5.4 Read path

| Hook | Source | Query | Cap |
| --- | --- | --- | --- |
| `useAIMonitoring` | `ai_monitoring_events` | `feature == X` and `createdAt >= since`, newest first | 1,000 + 1 sentinel |
| `useAIErrors` | `ai_monitoring_events` | `status == error`, optional feature, window | 500 + 1 sentinel |
| `useAdminAISessions` | collection group `ai_sessions` | `orderBy(completedAt desc)` | 500 + 1 sentinel |
| `useAIEvaluation` | static JSON | `fetch('/models/evaluation_report.json')` | whole artifact |

One extra document is requested from Firestore so the repository can distinguish `no more data` from `cap reached`. The read hooks expose `truncated`, `cappedAt` and the window start to the UI.

## 6. Admin surface

| Route | Page | Primary data |
| --- | --- | --- |
| `/admin/ai-monitoring` | Model Monitoring | recommendation events + static evaluation report |
| `/admin/ai-coach-monitoring` | AI Coach Monitoring | coach events + saved `ai_sessions` |
| `/admin/ai-errors` | AI Error Log | error-status events |

All three routes are guarded by the existing `manage_ai` permission. The navigation item is in `src/components/navigation/adminNav.ts`.

### Model Monitoring panels

- Plans generated, generation success, members using AI, inference latency, error events.
- Failure categories and explicit failure counts.
- Daily recommendation event volume.
- Predicted plan-category mix.
- Deployed-artifact registry and offline evaluation table.

### AI Coach Monitoring panels

- Saved sessions, members, total reps, average form, completion rate.
- Started / completed / interrupted / failed lifecycle.
- Inference latency from saved per-session sums.
- Session starts by exercise.
- Saved verdict distribution, with an explicit explanation of `insufficient data`.
- Failure signals and filterable saved-session history.

### AI Error Log panels

- Error event count, affected members, distinct categories, latest error, feature split.
- Error category breakdown and daily volume.
- Filterable, paginated event table.
- Retention and sanitisation notes.

## 8. Reliability and failure semantics

| Failure | Product impact | Monitoring impact |
| --- | --- | --- |
| Firestore unavailable / offline | None | Events dropped silently |
| Rules reject a write | None | Event lost; admin counts lower |
| Index missing | None | Admin page shows an index-required message |
| Evaluation JSON missing | None | Evaluation table shows an unavailable state; artifact HEAD checks flag missing files |
| One event has an unexpected field | None | Rules reject the event; other events unaffected |
| Admin query exceeds cap | None | UI labels the result as latest-N / capped |

No monitoring call is placed inside a `try` block whose `catch` changes product control flow. The AI feature decides success or failure first; telemetry is emitted afterwards.

## 9. Privacy boundaries

Stored:

- Firebase UID of the signed-in member.
- Session reference generated locally.
- Feature, event type, status, timestamp, app version.
- Model ID, model version, exercise key, predicted plan category.
- Aggregate confidence, latency, counts, reps, duration.
- Error category, stable error code, sanitised short message.

Never stored:

- Camera frames, video, image URLs or blobs.
- Pose landmarks or per-frame coordinates.
- Workout answers, goals, injuries, free text, or questionnaire content.
- Member name, email, photo, or support content.
- Stack traces or raw exception objects.

The AI Coach page states this in the UI footer: `No camera footage, frames or landmarks are persisted.`

## 11. Extension rules

When adding an event:

1. Add the literal to `AIMonitoringEventType` and `AI_EVENT_TYPES`.
2. Add the literal to `validAIMonitoringEvent()` in `firestore.rules`.
3. Keep the field within the existing allowlist, or update both the writer allowlist and the rules allowlist.
4. Emit only after the product outcome is known.
5. Add an aggregation test and, if the event is security-sensitive, a rules test.
6. Update this document and [AI Monitoring](./PHASE_4_AI_MONITORING.md).

When adding a metric:

1. Define its numerator and denominator explicitly.
2. Return `null` for undefined denominators.
3. Use stored events or saved sessions; never a constant.
4. Add the label that explains the data window and cap.
